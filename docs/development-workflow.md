# Development workflow

Guide for **AI coding agents** and human contributors. For architecture and coding rules, see [AGENTS.md](../AGENTS.md). For product scope, see [overview.md](overview.md).

---

## Before you change code

1. **Read repository instructions** — [AGENTS.md](../AGENTS.md), this file, and relevant [Cursor rules](../.cursor/rules/).
2. **Read product context** — [docs/overview.md](overview.md) and the current milestone (MVP 0 unless stated otherwise).
3. **Inspect existing implementation** — match naming, patterns, and directory layout before adding abstractions.
4. **Check the engineering backlog** — [engineering-baseline-backlog.md](backlog/engineering-baseline-backlog.md) for known gaps; do not rebuild infrastructure that is already planned or in progress.

---

## Critical rule: preserve existing choices

Do **not** replace an existing tool, convention, workflow, or architecture because another option is more common.

| Keep | Do not introduce instead |
|------|--------------------------|
| Ruff + pre-commit (backend) | Black, Flake8, or a parallel linter |
| Alembic migrations | `create_all()` or manual schema edits |
| FastAPI service-layer layout | New framework or fat routers |
| Docker Compose local stack | Alternate local orchestration without reason |
| Existing Makefile / task scripts | Duplicate task runners |

Replace something only when there is a **concrete technical problem** with the current solution.

---

## Standard workflow

Use this sequence for non-trivial work:

```text
1.  Read repository instructions (AGENTS.md, this file, Cursor rules)
2.  Read relevant product/architecture documentation
3.  Inspect existing implementation
4.  Identify the smallest appropriate change
5.  Propose a plan for non-trivial work (before large diffs)
6.  Implement
7.  Add or update tests (when test harness exists; see backlog)
8.  Run existing local quality checks
9.  Run relevant tests
10. Check database migrations if models changed
11. Review the diff (scope, secrets, unrelated edits)
12. Update documentation if behavior or architecture changed
13. Report what changed and what remains
```

Agents must **never rewrite infrastructure** merely to match a preferred stack.

## Implementation guidelines

### Scope

- Make the **smallest correct diff**. Do not modify unrelated files.
- Do not add dependencies unless they solve a concrete need.
- Align work with the **current milestone** in [overview.md](overview.md).

### Backend

- **Routers** (`backend/app/routers/`) — parse input, call services, return `ok()` envelope. No business rules.
- **Services** (`backend/app/services/`) — business logic, orchestration, domain rules.
- **Models** (`backend/app/models/`) — schema only.
- **Schemas** (`backend/app/schemas/`) — Pydantic v2 API contracts.
- Raise `AppError` for domain errors; follow [rest-api-standards.md](rest-api-standards.md).
- Use **sync** endpoints and DB access unless there is a justified async need.

### Frontend

- **Pages** — thin; route-level composition only.
- **Hooks** (`frontend/src/hooks/`) — UI state and orchestration.
- **Services** (`frontend/src/services/`) — API calls via `apiClient`.
- **Shared** (`frontend/src/shared/`) — reusable UI and utilities.
- All user-visible strings through **i18n keys** (`frontend/src/locales/`).
- Do not compute game outcomes in the frontend; display backend results.

### Game engine (future milestones)

Keep event logic **data-driven**:

```text
Event → Questions → Answers → Outcome conditions → Outcome effects → SimulationState
```

Do not hardcode individual events in HTTP endpoints or React components. See `.cursor/rules/game-engine.mdc`.

## Database and migrations

Agents **must not** run database queries or migration commands against a live database. See `.cursor/rules/no-database-queries.mdc`.

When models change:

1. Edit SQLAlchemy models in `backend/app/models/`.
2. Tell the user to autogenerate a migration:

   ```bash
   make makemigrations MSG='describe the change'
   ```

3. Review the autogenerated file under `backend/alembic/versions/`.
4. Tell the user to apply migrations:

   ```bash
   make migrate
   ```

**Never** hand-write new migration files from scratch (see `.cursor/rules/no-framework-scaffolding.mdc`). **Never** use `Base.metadata.create_all()` for schema changes.

## Quality checks

Run what exists today before submitting changes:

```bash
make pre-commit-run          # Ruff + file hooks (backend)
make lint                    # Ruff check only
make typecheck               # mypy on app/services and app/shared
make test                    # backend pytest (Docker)
make lint-frontend           # ESLint
make format-check-frontend   # Prettier check
cd frontend && npm run build # TypeScript + Vite build
```

With a local Python 3.12 environment: `pip install -e "./backend[dev]"` then `cd backend && pytest` and `mypy app/services app/shared`.

Future checks (ESLint, CI) are listed in [engineering-baseline-backlog.md](backlog/engineering-baseline-backlog.md).

## Secrets and configuration

- Never commit `.env`, credentials, or production secrets.
- Use [`.env.example`](../.env.example) for placeholders only.
- Production secrets belong in the deployment platform (target: Fly.io), not in source control.

## Documentation updates

Update docs when you change:

- Architecture or layer responsibilities
- API contracts (also [rest-api-standards.md](rest-api-standards.md))
- Local setup or commands ([README.md](../README.md))
- Agent conventions ([AGENTS.md](../AGENTS.md))

Do not duplicate content across files — **link** to the canonical doc.

Mark items complete in [engineering-baseline-backlog.md](backlog/engineering-baseline-backlog.md) only when the work is actually done. Never mark **human action required** items (Fly.io setup, GitHub secrets, first deploy) complete without user confirmation.

---

## Human action required

Agents **cannot** complete these without the user:

- Fly.io login, app creation, PostgreSQL provisioning, production secrets
- GitHub repository secrets and branch protection
- First production deployment and migration verification
- Running `make migrate` / `make makemigrations` on the user's machine (provide the command; user runs it)

---

## Pre-submit checklist

Before finishing a task, verify:

- [ ] Read [overview.md](overview.md) and [AGENTS.md](../AGENTS.md)
- [ ] Change scope is minimal and milestone-appropriate
- [ ] Business logic in services, not routers or React pages
- [ ] User-facing strings use gettext (backend) or i18n keys (frontend)
- [ ] Model changes have a migration path documented for the user
- [ ] No secrets or unrelated edits in the diff
- [ ] `make pre-commit-run` passes (backend changes)
- [ ] `make test` passes (backend changes)
- [ ] `make typecheck` passes (backend services/shared changes)
- [ ] `make lint-frontend` and `make format-check-frontend` pass (frontend changes)
- [ ] `npm run build` passes (frontend changes)
- [ ] Documentation updated if behavior or setup changed
