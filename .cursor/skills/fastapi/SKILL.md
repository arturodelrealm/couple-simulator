# FastAPI Backend Conventions

## Before You Start

1. **Read `AGENTS.md`** (or `agents.md`) at the project root if it exists. Follow any project-specific rules there in addition to this skill.
2. Inspect existing project structure (`app/`, `services/`, `shared/`, `alembic/`) and match established patterns before adding new code.

## Architecture

```
routers/     → thin HTTP layer (validation, auth, response mapping)
services/    → business logic
models/      → SQLAlchemy ORM models
schemas/     → Pydantic v2 request/response models
shared/      → reusable helpers and utilities
alembic/     → database migrations
```

| Layer | Responsibility |
|-------|----------------|
| **Endpoints** | Parse input, call service, return response. No business rules. |
| **Services** | All business logic, orchestration, and domain rules. |
| **Models** | Database schema only. |
| **Schemas** | API contracts (Pydantic v2). |

## SQLAlchemy 2.0

Use modern 2.0 style throughout:

```python
from uuid import UUID, uuid4

from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column

class User(Base):
    __tablename__ = "users"

    id: Mapped[UUID] = mapped_column(primary_key=True, default=uuid4)
    email: Mapped[str] = mapped_column(String(255), unique=True)
```

- Prefer **UUID primary keys** over auto-increment integers.
- Use `select()`, `session.execute()`, and `session.scalars()` — not legacy `session.query()`.
- Type-annotate columns with `Mapped[T]`.
- **Never call `Base.metadata.create_all()`** — schema changes go through Alembic only.

## Pydantic v2

```python
from pydantic import BaseModel, ConfigDict
from uuid import UUID

class UserCreate(BaseModel):
    email: str

class UserRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: UUID
    email: str
```

- Use `model_config = ConfigDict(from_attributes=True)` for ORM serialization.
- Use `model_validate()` / `model_dump()` — not v1 `from_orm()` / `dict()`.

## Thin Endpoints, Fat Services

**Endpoint** — delegate immediately:

```python
@router.post("/", response_model=UserRead, status_code=201)
def create_user(payload: UserCreate, db: Session = Depends(get_db)):
    return user_service.create_user(db, payload)
```

**Service** — owns the logic:

```python
def create_user(db: Session, payload: UserCreate) -> User:
    if user_repo.get_by_email(db, payload.email):
        raise ConflictError("Email already registered")
    return user_repo.create(db, payload)
```

## Async

Use **sync by default**. Switch to async only when there is a concrete need (e.g. async DB driver, concurrent I/O-bound external calls). Do not make endpoints async "just because it's FastAPI."

## Shared Helpers

| Situation | Location |
|-----------|----------|
| Reusable across modules | `shared/` directory |
| Specific to one module | Same file or local module |

Before writing a helper inline, check if an equivalent already exists in `shared/`. Before adding to `shared/`, confirm it will be reused — avoid polluting shared with one-off logic.

## Alembic Migrations

**Every model change requires a migration.** Never rely on `create_all()`.

### Whenever a database model changes

1. **Check whether a migration is required.** Not every code change needs one (e.g. renaming a Python attribute without changing the column). Any change to table structure, constraints, indexes, or column types does.
2. **Explain migration implications.** Tell the user what the migration will do: new tables/columns, altered types, added constraints, data backfills, etc.
3. **Warn about destructive migrations.** Flag operations that drop columns, drop tables, truncate data, or change types in ways that may lose data. Call these out explicitly before applying.
4. **Prefer renames over drop/add when appropriate.** If a column is being renamed, use `op.alter_column(..., new_column_name=...)` or an explicit rename — not drop + add, which destroys existing data.
5. **Keep models and migrations synchronized.** The ORM models and the latest migration must reflect the same schema. Never merge model changes without the corresponding migration.

After modifying models:

```bash
alembic revision --autogenerate -m "describe the change"
```

Review the generated migration for correctness, then apply:

```bash
alembic upgrade head
```

Always review autogenerated migrations — Alembic may suggest drop/add when a rename is intended.
